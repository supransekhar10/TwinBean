# Phase 2 Plan 03: Separate doctor-authorized patient detail streams

## Phase Goal

**As an** authorized doctor, **I want to** access synthetic CKD histories and a separately modeled simulated IoT stream stored in Firestore, **so that** I can review the two evidence sources without conflating them.

<objective>
Expand the tracer into a complete patient-detail read that preserves EHR/IoT separation from Firestore query through API serialization.

Purpose: Make one synthetic patient's longitudinal evidence available only to authorized doctors without merging sources, leaking storage objects, or issuing unbounded reads.
Output: Typed detail response, independent repository queries, protected detail route, and offline route/repository tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| doctor client → detail route | Untrusted token, patient ID, and event limit enter the protected API. |
| detail route → repository | Authorized typed requests enter persistent patient lookup. |
| repository → two Firestore subcollections | Privileged reads cross separately into EHR and IoT storage. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-2-06 | Elevation of Privilege | `GET /patients/{patient_id}` | high | mitigate | Apply unchanged require_doctor directly to the handler; test 401/403/200 and repository non-invocation on denial. |
| T-2-07 | Information Disclosure | Detail repository/serialization | high | mitigate | Validate stable patient IDs, serialize typed fields only, keep EHR/IoT responses distinct, and never expose snapshots or exception detail. |
| T-2-08 | Denial of Service | Detail history queries | medium | mitigate | Cap each stream at 500, reject invalid limits, short-circuit child reads for absent roots, and test query construction. |
| T-2-SC | Tampering | npm/pip/cargo installs | high | mitigate | Install no dependency; use existing FastAPI, Pydantic, Firebase Admin, and pytest surfaces only. |
</threat_model>

## Planner assumptions

- **FIRE-05:** Direct `Depends(require_doctor)` declarations on list and detail are sufficient and auditable; accepted by denial-before-repository tests for both endpoints.
- **DATA-02:** Separate repository queries and response keys are sufficient to prevent source conflation; accepted by fake path/type/order tests.
- **DATA-03:** Reading patient/EHR/IoT through the Firestore repository with no alternate adapter completes the in-scope persistence path; accepted by the combined backend suite and live checkpoint.
